# CLAUDE.md

Memoria técnica del proyecto para futuras interacciones con IA. Léelo antes de generar o modificar código en este repositorio.

## Qué es este proyecto

Sistema de reservaciones para una casa privada de renta ("Casa Brava Rentals"), de acceso exclusivo por invitación. Estado actual: **prototipo visual (esqueleto)**. No hay backend real conectado.

## Stack tecnológico

- **Next.js 16** (App Router, no Pages Router) con Turbopack.
- **React 19**.
- **TypeScript** en modo `strict`. No usar `any` salvo casos justificados.
- **Tailwind CSS v4** (configuración basada en CSS vía `@import "tailwindcss"` en [app/globals.css](app/globals.css); no existe `tailwind.config.js`, los tokens se definen con `@theme`).
- **Librerías headless permitidas** (ver detalle en "Qué NO hacer"): `lucide-react` (íconos del sistema), `react-day-picker` + `date-fns` (calendarios). Ninguna trae CSS propio importado — se estilizan 100% con Tailwind vía sus props `classNames`/`className`.
- Alias de imports: `@/*` apunta a la raíz del proyecto (ver `tsconfig.json`). Usar siempre `@/components/...`, `@/lib/...`, nunca rutas relativas largas (`../../../`).

## Convenciones de nomenclatura

- Componentes React: `PascalCase.tsx` dentro de `components/` (ej. `BookingSummary.tsx`).
- Rutas/páginas: carpetas en minúsculas y en español, siguiendo el idioma de la UI (ej. `app/reservar/page.tsx`, `app/pago-exitoso/page.tsx`).
- Funciones y variables: `camelCase`. Tipos e interfaces: `PascalCase`.
- Un componente por archivo. Exportación por defecto para componentes de página y de UI en `components/`.
- Datos mockeados centralizados en `lib/mock-data.ts` — no hardcodear precios, amenidades o textos de servicios directamente dentro de los componentes de página.

## Reglas de diseño

- **Mobile-first**: escribir las clases base pensando en mobile y usar prefijos (`sm:`, `md:`, `lg:`) para escalar hacia arriba. Nunca partir de un layout desktop y luego "achicar".
- Paleta minimalista en escala de grises (neutral-*) con acentos en negro (`neutral-900`) para botones primarios. Mantener esa consistencia al agregar nuevas vistas.
- **Íconos del sistema** (Navbar, `BackButton`, controles del carrusel, botones de UI en general) usan componentes de **`lucide-react`** (ej. `<User className="h-5 w-5" />`), no archivos `.svg` estáticos. Los `.svg` de `public/icons/system/` quedan obsoletos para este propósito — no se borran del repo por si algún flujo futuro los necesita, pero no se referencian desde componentes nuevos.
- **Íconos de amenidades** (la lista de amenidades de la casa en `public/icons/amenities/<categoría>/`) **siguen usando el formato estático actual**: tag `<img>` nativo apuntando al `.svg`, no `lucide-react` ni `next/image`. Esto es intencional — son ilustraciones curadas y personalizadas de la propiedad (íconos de cocina, alberca, etc.), no íconos genéricos de interfaz, y `lucide-react` no tiene equivalentes para la mayoría de ellas. El optimizador de imágenes de Next.js además rechaza `.svg` a menos que se habilite `dangerouslyAllowSVG` en `next.config.ts`, y no se ha activado esa opción — por eso siguen siendo `<img>` y no `next/image`. `next/image` sigue siendo el estándar para fotografías (`.jpeg`/`.png`) como en `Carousel.tsx`.
- Toda vez que se use `<Image fill>` (contenedor con tamaño fijo/relativo, foto que llena el espacio), agregar siempre la prop `sizes` con el ancho real que ocupará la imagen en cada breakpoint (ej. `sizes="(max-width: 640px) 100vw, (max-width: 1024px) 50vw, 33vw"` para una grilla `sm:grid-cols-2 lg:grid-cols-3`, o `sizes="(min-width: 768px) 700px, 100vw"` para un carrusel a ancho de contenedor fijo). Sin `sizes`, Next.js emite una advertencia de rendimiento y puede descargar una imagen más pesada de lo necesario. Reservar `priority` únicamente para la imagen que aparece arriba del fold en la carga inicial (ej. la primera foto del carrusel en `app/page.tsx`), no para imágenes que aparecen más abajo (como las de `ServiceCard.tsx`).
- **Calendarios** ([components/Calendar.tsx](components/Calendar.tsx), wrapper de `react-day-picker`): cualquier clase pensada para sobreescribir el estilo por defecto de una celda (`outside`, `disabled`, `range_start`/`range_end`/`range_middle`) debe llevar `!important` en **todas** sus propiedades (no solo la que a simple vista parece necesitarlo) — react-day-picker activa varios modificadores a la vez sobre la misma celda (ej. `selected` + `range_start`, u `outside` + `disabled`), y sin forzarlo el orden de generación de Tailwind decide cuál gana, no la clase semánticamente correcta (ver detalle en [DOCUMENTATION.md](DOCUMENTATION.md)). Para indicadores de disponibilidad día por día (verde disponible / rojo bloqueado), usar el patrón ya establecido en `AVAILABILITY_MODIFIERS_CLASS_NAMES` (exportado desde `Calendar.tsx`, integrado hoy solo en `SpaBookingForm.tsx` como prueba de concepto) en vez de inventar uno nuevo por componente.
- Componentes reutilizables van en `components/`; las páginas (`app/**/page.tsx`) solo componen esos componentes y manejan estado/routing, no deberían tener bloques grandes de markup propios.
- Los formularios y flujos con estado (login, reservación) son Client Components (`"use client"`) porque dependen de `useState`/`useRouter`. Las páginas puramente de presentación (home, pago exitoso) se mantienen como Server Components cuando sea posible.
- La protección de rutas por sesión **ya no se hace con un wrapper de componente** (el antiguo `components/ProtectedRoute.tsx` se eliminó): ahora corre en [middleware.ts](middleware.ts), del lado del servidor, antes de que la página renderice. Por eso ninguna página necesita ya un wrapper de auth en su JSX — `app/page.tsx`, `app/carrito/page.tsx` y las de `app/servicios/` quedaron como Server Components "limpios" (nunca tuvieron `"use client"`), y `app/reservar/page.tsx` sigue siendo Client Component por su propio estado (`useState`/`useRouter`, ver punto anterior), no por la protección de ruta. Ver la sección "Autenticación real con Supabase Auth + middleware" más abajo antes de agregar una ruta nueva que deba requerir sesión.

## Autenticación real con Supabase Auth + middleware (Huésped vs. Administrador)

El login mockeado (`localStorage`, sin verificar contraseña) fue **reemplazado por completo** por Supabase Auth con cookies, siguiendo el patrón oficial de `@supabase/ssr` para Next.js App Router. `role_type` (`admin` | `holder` | `guest`, ENUM de la migración — ver sección de infraestructura de Supabase) es ahora la fuente de verdad del rol de cada usuario, leído desde la tabla `profiles`.

- **Utilitarios de Supabase** ([lib/supabase/](lib/supabase)): cuatro archivos, uno por contexto de ejecución — nunca importar el cliente equivocado para el contexto en el que se está:
  - [lib/supabase/env.ts](lib/supabase/env.ts): valida `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY` una sola vez y las exporta ya tipadas como `string` (no `string | undefined`) — los clientes de abajo importan de aquí en vez de leer `process.env` directamente. **Nunca** agregar aquí la validación de `SUPABASE_SERVICE_ROLE_KEY` (ver `admin.ts` abajo) — este archivo lo importa `client.ts`, que corre en el navegador.
  - [lib/supabase/client.ts](lib/supabase/client.ts): `createClient()` con `createBrowserClient` — para Client Components (`"use client"`). Se usa en `AuthContext.tsx` y en `app/login/page.tsx`.
  - [lib/supabase/server.ts](lib/supabase/server.ts): `createClient()` (async) con `createServerClient` + `next/headers.cookies()` — para Server Components, Server Actions y Route Handlers. Crear una instancia nueva por request, nunca reutilizar.
  - [lib/supabase/middleware.ts](lib/supabase/middleware.ts): `updateSession(request)` — la lógica real de refresco de sesión y los guards de ruta (ver abajo), consumida por `middleware.ts` en la raíz.
  - [lib/supabase/admin.ts](lib/supabase/admin.ts): `createAdminClient()` — cliente con la **Service Role Key** (`SUPABASE_SERVICE_ROLE_KEY`, no `NEXT_PUBLIC_*`), que bypassa RLS y habilita la Auth Admin API (`supabase.auth.admin.*`). **Server-only, uso administrativo exclusivamente** — hoy solo lo consume [app/admin/actions.ts](app/admin/actions.ts) (ver sección "CRUD de usuarios" más abajo). Nunca importarlo desde un Client Component. A diferencia de los otros tres, usa `createClient` de `@supabase/supabase-js` directamente (no `createServerClient` de `@supabase/ssr`) porque no gestiona cookies ni sesión de usuario — siempre actúa con privilegios de servicio, con `autoRefreshToken`/`persistSession` desactivados explícitamente. Requiere agregar `SUPABASE_SERVICE_ROLE_KEY` a `.env.local` (ya documentado ahí mismo con un comentario; el valor se obtiene con `npx supabase status` tras `npx supabase start`, campo "service_role key", o desde Supabase Studio → Settings → API).
  - Los cuatro clientes pasan `"public"` explícito como segundo genérico (`createBrowserClient<Database, "public">(...)`, etc.) — sin esto, la inferencia de schema de `@supabase-js` se rompe con nuestro `database.types.ts` (no incluye el campo `__InternalSupabase` que versiones recientes de supabase-js esperan para inferir el schema por default) y cualquier `.from("tabla")` deja de tipar. Si se regenera `database.types.ts` con una versión del CLI que sí emita `__InternalSupabase`, este workaround podría dejar de ser necesario, pero no hace daño dejarlo.
- **`middleware.ts`** (raíz del proyecto): refresca la sesión de Supabase en cada navegación y aplica los guards de ruta del lado del servidor — reemplaza por completo al antiguo `components/ProtectedRoute.tsx` (eliminado), que redirigía en el cliente después de que la página ya había cargado.
  - ⚠️ **Next.js 16 renombró esta convención de archivo a `proxy.ts`** (función exportada como `proxy` en vez de `middleware`) — `middleware.js` quedó deprecado pero **sigue funcionando** vía compatibilidad hacia atrás (confirmado en `node_modules/next/dist/build/utils.js`, `isMiddlewareFilename`; y en dev, `next dev` imprime el warning de deprecación pero corre el archivo con normalidad). Se mantuvo el nombre `middleware.ts` porque así se pidió explícitamente. Si en una futura versión de Next.js se retira el soporte legacy, el único cambio necesario es renombrar el archivo a `proxy.ts` y la función a `proxy` (hay codemod oficial: `npx @next/codemod@canary middleware-to-proxy .`).
  - Rutas protegidas por prefijo (sin importar el rol): `/reservar`, `/perfil`, `/carrito`, `/servicios/*` — sin sesión, redirige a `/login`.
  - **`/` (home) también requiere sesión activa** — es una ruta de **coincidencia exacta** (`PROTECTED_EXACT_PATHS`, evaluada con `pathname === "/"`), separada de `PROTECTED_PREFIXES` (que usa `startsWith`) a propósito: si `"/"` viviera en la lista de prefijos, `startsWith("/")` haría match de **cualquier** pathname (incluyendo `/login`, `/register`), generando un bucle de redirección infinito. Sin sesión, `/` redirige a `/login` igual que el resto de rutas protegidas.
    - ⚠️ Esto revirtió un cambio de una iteración anterior de este mismo archivo, donde `/` se dejó deliberadamente pública al migrar a Supabase Auth. Se detectó como bug de seguridad (el sistema es de acceso exclusivo por invitación) y se corrigió — si se vuelve a tocar esta lógica, `/` **debe** quedar protegida; no repetir ese error.
  - `/admin` requiere sesión **y** `role === "admin"` en `profiles` — la verificación hace un `select("role")` a la tabla `profiles` dentro del propio middleware; si el rol no es exactamente `"admin"` (incluye `"guest"`, `"holder"`, o si el perfil no se pudo leer), redirige a `/`. Es *fail closed*: cualquier caso ambiguo se trata como no autorizado. Como `/` ahora también requiere sesión, este redirect no genera bucle: el usuario que llega aquí ya tiene una sesión válida (solo le falta el rol), así que `/` se resuelve sin rebotar a `/login`.
  - `/login` y `/register` no están en ninguna lista de rutas protegidas — deben seguir siendo 100% accesibles sin sesión (son, junto con cualquier futura ruta de callback de auth, la válvula de escape que evita el bucle infinito).
  - `getUser()` (no `getSession()`) es lo que decide acceso en el middleware — valida el JWT contra Supabase Auth en vez de solo decodificarlo localmente, por eso es el único punto realmente "de servidor" del guard.
- **[lib/AuthContext.tsx](lib/AuthContext.tsx)**: ya no usa `localStorage`. `AuthProvider` (montado en [app/layout.tsx](app/layout.tsx)) expone `useAuth()` con `{ user, profile, isLoading, login(email, password), logout() }`:
  - `user` es el `User` de `@supabase/supabase-js` (sesión de Auth); `profile` es la fila completa de `profiles` (tipo `Profile`, exportado desde este mismo archivo) para ese usuario — incluye `role`, `status`, `first_name`, etc.
  - Hidratación inicial vía `supabase.auth.getSession()` al montar, y `supabase.auth.onAuthStateChange(...)` mantiene `user`/`profile` sincronizados ante login/logout/refresh de token (incluido lo que pase en otra pestaña).
  - `loadProfile(user)` hace el `select("*")` a `profiles` y usa un contador (`profileRequestId`, `useRef`) para descartar respuestas "viejas" si el usuario cambia de sesión mientras un fetch anterior sigue en vuelo — es la defensa contra condiciones de carrera en el propio contexto.
  - **`login(email, password)` reutiliza `loadProfile` en vez de disparar su propia consulta a `profiles`** — se detectó en pruebas manuales que hacer una consulta aparte (`select("role")`) justo después de `signInWithPassword` corre una carrera real contra la consulta que dispara `onAuthStateChange` para el mismo evento `SIGNED_IN`: el cliente de Supabase todavía está propagando el token nuevo internamente, y una de las dos peticiones concurrentes puede recibir `401`. La solución fue consolidar a un solo camino de fetch (`loadProfile`) con **un reintento** si el primer intento no devuelve perfil — no enmascara errores reales porque las credenciales inválidas ya se filtran antes, en la respuesta de `signInWithPassword`. Si se toca esta función, no volver a introducir una segunda query paralela a `profiles` sin ese mismo cuidado.
  - `logout()` es `async` (llama a `supabase.auth.signOut()`) — cualquier caller (`Navbar.tsx`, `app/perfil/page.tsx`) debe hacer `await logout()` antes de redirigir, no tratarlo como función síncrona.
- **[app/login/page.tsx](app/login/page.tsx)**: sigue validando formato de correo y contraseña no vacía en el cliente antes de llamar a `login()` (esa validación de formato no cambió). Al llamar a `login()`, si hay error se traduce con `translateAuthError()` (mensajes de `AuthApiError` de Supabase, ej. "Invalid login credentials" → "Correo o contraseña incorrectos.") y se muestra en el mismo lugar que antes (bajo el input de contraseña) — los estilos de error no cambiaron. Si el login es exitoso, redirige a `/admin` o `/` según el `role` que devuelve `login()`, y llama a `router.refresh()` para que los Server Components de la página destino no queden con datos de una sesión vieja en caché.
- La tabla de reservaciones del panel de administración ([components/ReservationsTable.tsx](components/ReservationsTable.tsx), montada en `/admin/reservations`) y la de usuarios ([components/UsersTable.tsx](components/UsersTable.tsx)) ya no son mock — ver "CRUD de usuarios" y "CRUD de reservaciones" más abajo. `mockReservations`/`MockReservation`/`ReservationStatus` (el tipo mock, no el ENUM real de la base de datos) se eliminaron de `lib/mock-data.ts` por quedar sin ningún uso, mismo criterio que ya se había aplicado a `mockUsers`.
- **Navbar** ([components/Navbar.tsx](components/Navbar.tsx)) sigue siendo reactivo a `useAuth().user` (el `User` real de Supabase): sin sesión muestra "Iniciar sesión"; con sesión muestra "Perfil" y "Cerrar sesión" (ahora `async`).
- **Seed de usuarios de prueba** (`supabase/seed.sql`, ver infraestructura de Supabase): los tres usuarios sembrados (`admin@test.com`, `maria.gomez@example.com`, `carlos.ruiz@example.com`) tienen la contraseña de desarrollo `changeme123` en el entorno local — no es un secreto real, solo sirve para probar el login contra `auth.users` local.

## CRUD de usuarios (panel de administración)

**Fase 1 y Fase 2 completas**: [app/admin/page.tsx](app/admin/page.tsx) y [components/UsersTable.tsx](components/UsersTable.tsx) ya no leen `mockUsers` — la sección "Usuarios invitados" del panel de administración lee, crea, edita (rol/estado) y elimina filas reales de `profiles` + `auth.users`. `mockUsers`/`MockUser`/`UserRole`/`UserStatus` se eliminaron de `lib/mock-data.ts` por quedar sin ningún uso. `ReservationsTable` pasó por el mismo proceso en una fase posterior — ver "CRUD de reservaciones" más abajo.

- **[app/admin/page.tsx](app/admin/page.tsx)**: Server Component `async` — con el cliente estándar de servidor ([lib/supabase/server.ts](lib/supabase/server.ts), autenticado vía cookies) hace en paralelo (`Promise.all`) el `select("*")` de `profiles` (ordenado por `created_at` descendente) y `supabase.auth.getUser()`, y pasa ambos a `UsersTable` como `users`/`currentUserId` — este último es lo que le permite a la UI deshabilitar "Eliminar" en la fila del propio admin (ver más abajo). Si el fetch de `profiles` falla, muestra un mensaje de error inline en vez de romper la página. La sección "Reservaciones" ya no se renderiza aquí — es solo una tarjeta con un link a `/admin/reservations` (ver "CRUD de reservaciones" más abajo).
- **[app/admin/actions.ts](app/admin/actions.ts)** (`"use server"`): Server Actions consumidas directamente por `UsersTable.tsx` (Next.js las expone como RPC al cliente automáticamente). Las tres devuelven `{ success: true } | { error: string }` (nunca lanzan hacia el caller — todo el cuerpo va en `try/catch`) y llaman a `revalidatePath("/admin")` al terminar con éxito, para que `app/admin/page.tsx` vuelva a hacer el fetch en el siguiente render.
  - `requireAdmin()`: guard compartido — lee la sesión con el cliente estándar (`lib/supabase/server.ts`) y verifica `role === "admin"` en `profiles`, mismo criterio *fail closed* que el guard de `/admin` en `lib/supabase/middleware.ts`. Devuelve el cliente autenticado (para que la action que la llamó lo reutilice en vez de crear una segunda conexión) **y el `userId` del propio admin** — necesario para el guard anti-auto-eliminación de `deleteUser`. Vive en [lib/supabase/require-admin.ts](lib/supabase/require-admin.ts) (extraído de aquí, donde antes vivía privado, para que `app/admin/reservations/actions.ts` lo reutilice sin duplicar el guard — ver "CRUD de reservaciones" más abajo).
  - `createUser(email, firstName, lastName1, lastName2, role)` — **Fase 2: ya no invita por correo, crea la cuenta directamente**. Usa **`createAdminClient()`** (Service Role Key) para llamar a `supabase.auth.admin.createUser({ email, password: DEFAULT_TEMP_PASSWORD, email_confirm: true })` — `email_confirm: true` salta la confirmación por correo, así que la cuenta queda lista para iniciar sesión de inmediato con la contraseña temporal fija `DEFAULT_TEMP_PASSWORD` (`"changeme123"`, la misma constante de desarrollo que `supabase/seed.sql`). Si la creación de Auth tiene éxito, inserta la fila en `profiles` con el mismo `id` devuelto (mismo cliente admin). Si el `insert` en `profiles` falla, **compensa borrando el usuario de Auth recién creado** (`admin.auth.admin.deleteUser`) para no dejar un usuario huérfano (con cuenta pero sin perfil) que dejaría ese correo "ocupado" y bloquearía cualquier reintento.
    - ⚠️ **Contraseña temporal fija — aceptable solo en este prototipo**: `DEFAULT_TEMP_PASSWORD` es la misma para *toda* cuenta creada desde `/admin`, conocida de antemano por cualquiera con acceso al código (igual que ya pasaba con los usuarios sembrados por `seed.sql`). Es una simplificación deliberada para un sistema de acceso invitado con un puñado de usuarios de confianza (familia/staff), donde el admin comparte la contraseña directamente con la persona. **Antes de cualquier despliegue real** hay que reemplazar esto por: (a) forzar cambio de contraseña en el primer login, (b) generar una contraseña aleatoria por usuario y comunicarla fuera de banda, o (c) volver al flujo de invitación por correo (`inviteUserByEmail`, usado en la Fase 1 de este mismo CRUD) para que la persona elija su propia contraseña. No se implementó ninguna de las tres porque no se pidió — este aviso es la referencia de qué falta si se retoma.
    - `translateCreateError()` traduce el único error que un admin puede provocar realmente desde este formulario (correo duplicado, `"already been registered"` → "Ya existe un usuario con este correo."); cualquier otro cae a un mensaje genérico en vez de exponer texto interno del proveedor — mismo criterio que `translateAuthError` en `app/login/page.tsx`.
  - `updateUser(userId, { role?, status?})`: a diferencia de `createUser`, usa el **cliente estándar** (el de la propia sesión del admin, ya autenticado) — no requiere la Auth Admin API, solo un `UPDATE` sobre una fila existente de `profiles`. **Guard anti-auto-modificación**: si `auth.userId === userId` (el admin intenta editar su propio rol o estado), devuelve `{ error: "No puedes modificar tu propio rol o estado." }` antes de tocar la base — sin este guard, el único admin podría quitarse el rol `admin` o suspenderse (`status: "invitado"`) a sí mismo y quedar sin acceso a `/admin` en su siguiente navegación, recuperable solo interviniendo la base de datos a mano (mismo tipo de auto-lockout que ya bloqueaba `deleteUser`). La UI ya deshabilita los selects de "Rol" y "Estado" en el modal de edición cuando el usuario editado es el propio admin (ver abajo), pero **la Server Action es el límite real**, no la UI.
  - `deleteUser(userId)` (**nuevo — Fase 2**): usa `createAdminClient()` para llamar a `admin.auth.admin.deleteUser(userId)`. **No borra `profiles` por separado** — `profiles.id` es FK a `auth.users(id)` con `on delete cascade` (ver migración inicial), así que borrar el usuario de Auth ya elimina su perfil automáticamente. La excepción es un `profile` huérfano cuyo usuario de Auth ya no existía (`error.status === 404` o mensaje `"not found"`): ahí sí se hace un `delete` explícito sobre `profiles` para no dejar una fila que ningún flujo normal puede volver a tocar. **Guard duro contra auto-eliminación**: si `auth.userId === userId` (el admin intenta borrarse a sí mismo), devuelve `{ error: "No puedes eliminar tu propia cuenta." }` antes de tocar Auth — sin este guard, el único admin podría dejar el panel sin nadie que pueda entrar, recuperable solo interviniendo la base de datos a mano. La UI ya deshabilita el botón "Eliminar" en la propia fila (ver abajo), pero **la Server Action es el límite real**, no la UI.
- **[components/UsersTable.tsx](components/UsersTable.tsx)**: ya no tiene `useState` espejando la prop `users` — recibe `Profile[]` directo de `app/admin/page.tsx` y renderiza esa prop tal cual; el refresco tras una action llega solo por el `revalidatePath` de arriba, no por estado local. Tres modales, cada uno con su propio `useTransition` (`isUpdatePending`/`isCreatePending`/`isDeletePending`) para deshabilitar botones y mostrar "Guardando…"/"Creando…"/"Eliminando…" mientras la Server Action está en vuelo, y su propio estado de error mostrado dentro del modal si la action devuelve `{ error }`:
  - **Modal "Editar usuario"**: solo edita `role` y `status` (no `nombre`/`email`) — a propósito, porque `updateUser` no soporta esos campos. Correo se muestra de solo lectura como referencia. Si el usuario editado es el propio admin logueado (`user.id === currentUserId`), los `<select>` de "Rol" y "Estado" vienen `disabled` y se muestra un aviso ("No puedes modificar tu propio rol o estado.") junto con el botón "Guardar cambios" también deshabilitado — refuerzo de UX del guard real que ya hace `updateUser` en el servidor.
  - **Modal "Crear usuario"** (renombrado en Fase 2 — antes "Invitar usuario"/`InviteUserModal`; el nombre cambió porque ya no se envía ningún correo, sería engañoso seguir llamándolo "invitar"): botón "Crear usuario" arriba de la tabla. Pide correo, nombre(s), apellido paterno, apellido materno (opcional) y rol; su copy explica desde antes de enviar que la cuenta queda activa con la contraseña temporal `changeme123`, para que el admin sepa qué comunicarle a la persona. Llama a `createUser` al enviar.
  - **Modal "Eliminar usuario"** (nuevo — Fase 2): botón "Eliminar" (estilo rojo, `DANGER_BUTTON_CLASS`, junto a "Editar" en la columna Acciones) abre un modal de confirmación con el nombre del usuario y una advertencia de que la acción no se puede deshacer; llama a `deleteUser` solo al confirmar dentro del modal, nunca directo desde la fila. El botón "Eliminar" de la propia fila del admin viene `disabled` (con `title="No puedes eliminar tu propia cuenta"` para el tooltip nativo) comparando `user.id === currentUserId` — refuerzo de UX del guard real que ya hace `deleteUser` en el servidor.
  - `RoleBadge` es exhaustivo sobre las 3 variantes de `role_type` (`admin`/`holder`/`guest`, vía `Record<Profile["role"], string>` para labels y clases) — **`role: "holder"` es asignable desde este panel** (crear o editar), aunque un usuario con ese rol sigue sin ninguna pantalla propia distinta en el resto de la app (sigue viendo la misma experiencia de huésped).
  - El tipo `Profile` (`Database["public"]["Tables"]["profiles"]["Row"]`) se reutiliza desde [lib/AuthContext.tsx](lib/AuthContext.tsx) (`import type { Profile } from "@/lib/AuthContext"`) en vez de redeclararlo — única fuente de verdad para la forma de una fila de `profiles` en todo el frontend.
- **⚠️ RLS sigue deshabilitado en `profiles`** (ver TODO pendiente en la sección de infraestructura de Supabase) — este CRUD funciona hoy porque el guard de autorización vive **en la aplicación** (`requireAdmin()` dentro de cada Server Action), no en la base de datos. Eso protege la superficie de la app (nadie sin rol admin puede invocar estas actions desde la UI), pero **no cierra el hueco de fondo**: cualquier cliente con la `anon key` (ej. desde la consola del navegador) todavía podría leer o escribir `profiles` directamente contra Supabase, sin pasar por `app/admin/actions.ts` en absoluto. Cuando se cree la migración de políticas RLS pendiente, `updateUser` (que usa el cliente de sesión estándar, no el admin) va a necesitar una política explícita tipo "los admins pueden actualizar cualquier profile" — sin ella, ese `UPDATE` empezaría a fallar silenciosamente (una escritura bloqueada por RLS no lanza error, solo afecta 0 filas). `createUser`/`deleteUser` no se ven afectados porque usan la Service Role Key, que siempre bypassa RLS.
- **Variable de entorno**: `SUPABASE_SERVICE_ROLE_KEY` en `.env.local` (ver el comentario agregado ahí mismo, y el detalle en el bullet de `admin.ts` más arriba). Sin ella, `createAdminClient()` lanza un error claro (capturado por el `try/catch` de `createUser`/`deleteUser`, se traduce en un `{ error }` legible en el modal) en vez de fallar de forma críptica.

## CRUD de reservaciones (panel de administración)

El panel de administración tiene una segunda ruta, [app/admin/reservations/page.tsx](app/admin/reservations/page.tsx) (enlazada desde `/admin` con un botón "Ver reservaciones" — ya no embebida ahí como antes), con CRUD real completo sobre la tabla `reservations`. Reemplaza por completo a `mockReservations`, eliminado de `lib/mock-data.ts`.

- **Dos estados independientes**: `status` (`pendiente` | `confirmada` | `cancelada` | `finalizada`) describe el ciclo de vida operativo de la reserva; `payment_status` (`pendiente` | `parcial` | `completado` | `reembolsado`, columna y ENUM `payment_status_type` nuevos, agregados en la migración `supabase/migrations/20260902053910_add_payment_status_and_finalizada_rename.sql`) describe el cobro, por separado. Se modelaron como dos columnas independientes — no una derivada de la otra — a propósito, para poder introducir anticipos/pagos parciales más adelante (ej. `payment_status: "parcial"` con una reserva todavía `pendiente` o ya `confirmada`) sin tocar el ciclo de vida de la reserva en sí. El modal de edición de [components/ReservationsTable.tsx](components/ReservationsTable.tsx) los expone como dos `<select>` independientes, cada uno cambiable sin afectar al otro.
  - ⚠️ **Renombre de ENUM**: el valor `pasada` de `reservation_status` (de la migración inicial) se renombró a `finalizada` en esta misma migración (`alter type ... rename value 'pasada' to 'finalizada'`), para que la base de datos use el mismo vocabulario que la UI. Fue seguro de hacer porque `reservations` nunca había sido consultada por ningún componente real hasta esta fase — solo un tipo mock no relacionado (`ReservationStatus` en `mock-data.ts`, ya eliminado) usaba ese mismo string por coincidencia.
- **Validación de fechas y prevención de solapamiento** (`app/admin/reservations/actions.ts`):
  - `validateDates(checkIn, checkOut)` exige que `check_out` sea posterior a `check_in`, comparando los strings ISO `yyyy-MM-dd` directamente en vez de construir `Date` (mismo motivo que la sección de `Calendar.tsx` más abajo documenta sobre el bug de zona horaria) — es una validación de UX con mensaje en español antes de tocar la base; el `check` constraint `reservations_check_out_after_check_in` de la migración inicial sigue siendo la garantía real del lado de la base de datos.
  - `hasOverlappingConfirmedReservation(supabase, checkIn, checkOut, excludeId?)` es la única función de solapamiento del sistema, reutilizada igual por `createReservation` y `updateReservation`: consulta `reservations` donde `status = 'confirmada'` y `deleted_at is null`, con `check_in < checkOut and check_out > checkIn` (intervalo semi-abierto — un check-out no choca con un check-in el mismo día). Como el proyecto es de una sola propiedad (no existe tabla `properties`, ver el bullet de abajo), la consulta no filtra por propiedad — todas las reservaciones compiten por el mismo calendario.
  - **El chequeo corre en dos disparadores, no solo cuando cambian las fechas**: además de correr siempre que `check_in`/`check_out` vengan en el payload (create o update), `updateReservation` también lo corre cuando el `status` efectivo resultante es `'confirmada'`, aunque el payload no toque fechas. No es un detalle menor: el modal de edición de `ReservationsTable.tsx` **solo** manda `{status, payment_status}` (nunca fechas, ver el bullet de arriba), así que el camino real por el que una reserva pasa de `pendiente` a `confirmada` en la UI de hoy es exactamente ese — sin este segundo disparador, dos reservas `pendiente` con fechas ya cruzadas podrían confirmarse una tras otra sin que el sistema lo detectara nunca, justo el doble-booking que esta funcionalidad existe para evitar.
- **Soft delete, no hard delete — auditado y blindado**: `deleteReservation` hace estrictamente `update({ deleted_at: new Date().toISOString() })` sobre la fila, nunca un `DELETE` físico — no existe ningún camino en `app/admin/reservations/actions.ts` que borre una fila de `reservations` de forma permanente. Se decidió así porque `spa_bookings`, `food_bookings` y `wine_orders` tienen `reservation_id references reservations(id) on delete cascade` — un `DELETE` real sobre una reservación se llevaría entre manos, sin aviso, el historial de todos los servicios adicionales asociados a ella. Usa la misma columna `deleted_at` ya documentada desde la migración inicial (ver "Modelo relacional" más abajo). Toda lectura de `reservations` que expone filas al cliente filtra explícitamente `.is("deleted_at", null)` — hoy la única (`getReservations()`), y cualquier consulta de lectura nueva que se agregue a este archivo debe mantener el mismo filtro; una reservación con soft delete nunca debe llegar a la UI. En la UI, el botón "Eliminar" abre un modal de **doble confirmación en dos pasos** (resumen → "Continuar" → advertencia final → "Sí, eliminar reserva") antes de llamar a la Server Action.
- **"Casa Brava" como propiedad estática**: el esquema no tiene ninguna tabla `properties` — todo el sistema es una sola casa. En vez de inventar una tabla nueva sin que se pidiera explícitamente, `/admin/reservations` muestra "Casa Brava" como subtítulo fijo de la página (una sola vez), no como columna repetida idéntica en cada fila de la tabla.
  - **Puerta abierta para bloques de mantenimiento (solo documentado, no implementado)**: la regla de solapamiento de arriba ya es genérica — bloquea por rango de fechas y `status = 'confirmada'`, sin mirar quién es el huésped. Eso significa que agregar bloques de mantenimiento al calendario (fechas en las que la casa no está disponible sin que haya un huésped real) no requeriría tocar `hasOverlappingConfirmedReservation` en absoluto: bastaría con permitir que `reservations.guest_id` sea nullable (o agregar un discriminador tipo `reservation_type: "guest" | "maintenance"`) para que una fila de mantenimiento sin huésped participe en la misma consulta y bloquee esas fechas para nuevas reservaciones, igual que lo haría cualquier reservación confirmada de un huésped real.
- **`requireAdmin()` compartido**: se extrajo de `app/admin/actions.ts` (donde antes vivía privado) a [lib/supabase/require-admin.ts](lib/supabase/require-admin.ts) — mismo comportamiento fail-closed de siempre — para que `app/admin/reservations/actions.ts` lo reutilice sin duplicar el guard de autorización. `app/admin/actions.ts` ahora importa de ahí en vez de definirlo localmente.
- **Los cuatro Server Actions** de `app/admin/reservations/actions.ts` (`getReservations`, `createReservation`, `updateReservation`, `deleteReservation`) siguen el mismo contrato que las de usuarios: `{ success: true } | { error: string }` (o `{ data } | { error }` para la lectura), try/catch en todo el cuerpo, `revalidatePath("/admin/reservations")` al terminar con éxito.
  - `getReservations()` hace el JOIN con `profiles` (alias `guest`) y `fare_types` (alias `fare_type`) en el mismo `select`, ordenado por `check_in` ascendente. El tipo de retorno (`ReservationWithRelations`) se autoría a mano en el propio archivo de actions — Supabase no infiere en profundidad selects con alias a partir de `lib/database.types.ts` — con una aserción de tipo justificada sobre el resultado.
  - `updateReservation(id, updates)` acepta genéricamente cualquier campo de la reserva (fechas, huésped, tarifa, monto, status, payment_status), aunque el modal de edición de esta fase solo mande `status`/`payment_status` — el resto de campos (huésped, fechas, tarifa, monto) solo se fijan al crear, todavía no hay UI para editarlos después.
  - El modal "Crear reservación" calcula un monto total sugerido con la misma fórmula que `components/BookingSummary.tsx` (noches × tarifa por noche + recargo de la tarifa elegida + depósito de garantía, usando `property_settings`/`fare_types` reales), pero el campo queda editable — un admin puede ajustarlo a mano (ej. un descuento) sin que se siga recalculando después.
- **⚠️ Mismo caveat de RLS que `profiles`**: la autorización de este CRUD también vive solo en la aplicación (`requireAdmin()` en cada action), no en la base de datos — `reservations` sigue sin políticas RLS (ver el TODO pendiente en la migración inicial). Cualquier cliente con la `anon key` todavía podría leer o escribir `reservations` directamente, sin pasar por estas Server Actions.

## Carrito de servicios adicionales (`CartContext`)

Los tres servicios adicionales (SPA/Masajes, Comida, Paquete de Vinos) tienen flujos de reserva propios y un carrito global, todo mockeado — sigue sin haber backend ni procesador de pagos reales:

- **Datos mockeados** (en `lib/mock-data.ts`, junto al resto): `SPA_MASSEUSES` (masajistas con `availableDays`/`availableTimes` simulados), `SPA_SESSION_PRICE`; `MEAL_TYPES`, `FOOD_MENU_OPTIONS` (`Record<MealType, MenuOption[]>`), `FOOD_AVAILABLE_DATES`; `WINE_BOTTLES`, `WINE_PACKAGE`. Los días disponibles (`availableDays` de cada masajista y `FOOD_AVAILABLE_DATES`) son fechas ISO simuladas (ej. `"2026-09-04"`), formateadas para mostrarse con la función `formatSimulatedDate(isoDate)` (también en `mock-data.ts`), no con un selector de fecha nativo — es intencional, ya que representan disponibilidad simulada, no un calendario real.
- **Tipos de detalle**: `SpaReservation`, `FoodReservation` y `WineOrder` (este último contiene `bottles: WineOrderBottle[]` + `packageQuantity`, para soportar botellas individuales y el paquete de 4 en un mismo pedido). El tipo `CartItem` es una unión discriminada por `serviceType` (`"spa" | "comida" | "vinos"`) que envuelve uno de esos detalles junto con `id`, `quantity` y `totalPrice`.
- **Estado global**: [lib/CartContext.tsx](lib/CartContext.tsx) expone `CartProvider` (montado en [app/layout.tsx](app/layout.tsx), anidado dentro de `AuthProvider` y envolviendo Navbar/main/Footer) y el hook `useCart()` con `{ items, isLoading, addToCart, removeFromCart, clearCart, totalPrice, totalItems }`. Sigue el mismo patrón que `AuthContext`: persiste en `localStorage` bajo la clave `casabrava_cart`, se hidrata en un `useEffect` al montar (con el mismo `eslint-disable-next-line react-hooks/set-state-in-effect` justificado, ver sección siguiente), y expone `isLoading` para evitar parpadeos.
- **Generación de ids de item**: `generateCartItemId(prefix)` (exportada desde `lib/CartContext.tsx`) vive fuera de cualquier componente/hook a propósito — `Date.now()` es una función impura y el lint `react-hooks/purity` (parte de `eslint-config-next` vía React Compiler) marca error si se llama directamente dentro del cuerpo de un componente, incluso en un handler anidado como `handleAddToCart`. Cualquier función nueva que necesite generar ids con `Date.now()`/`Math.random()` dentro de un componente debe extraerse igual, a un helper de módulo fuera de la función del componente.
- **Flujos de reserva** (Client Components, uno por servicio): [components/SpaBookingForm.tsx](components/SpaBookingForm.tsx), [components/FoodBookingForm.tsx](components/FoodBookingForm.tsx) y [components/WineBookingForm.tsx](components/WineBookingForm.tsx), montados respectivamente en `app/servicios/spa/page.tsx`, `app/servicios/comida/page.tsx` y `app/servicios/vinos/page.tsx` (Server Components "limpios", sin ningún wrapper de auth en su JSX — `/servicios/*` está protegida por `middleware.ts`, ver la sección de autenticación). Cada uno calcula su propio `totalPrice` y llama a `addToCart()` al enviar; tras agregar, muestran [components/AddedToCartBanner.tsx](components/AddedToCartBanner.tsx) (mensaje + link a `/carrito`) como feedback visual, sin redirigir automáticamente, para permitir seguir agregando servicios.
- **Enlace desde el Home**: [components/ServiceCard.tsx](components/ServiceCard.tsx) ahora incluye un botón "Reservar" que enlaza a `/servicios/${service.id}` — por eso los `id` de `ADDITIONAL_SERVICES` (`"spa"`, `"comida"`, `"vinos"`) deben coincidir exactamente con las carpetas de ruta bajo `app/servicios/`.
- **Página del carrito** ([app/carrito/page.tsx](app/carrito/page.tsx)): Server Component "limpio" (sin wrapper de auth — protegida por `middleware.ts`) que monta [components/CartView.tsx](components/CartView.tsx) (Client Component con toda la interactividad: listado vía [components/CartItemRow.tsx](components/CartItemRow.tsx), eliminar item, total y botón "Pagar servicios"). "Pagar servicios" llama a `clearCart()` y redirige a `/pago-exitoso`, igual que el flujo de `/reservar` — no procesa ningún cobro real.
- **Navbar**: [components/Navbar.tsx](components/Navbar.tsx) agrega un botón de carrito (`/icons/system/cart.svg`, ya existente en `public/icons/system/`) entre el logo y Perfil, con un badge que muestra `useCart().totalItems` cuando es mayor a 0, y enlaza a `/carrito`.

Al conectar Stripe real, el checkout de `/carrito` deberá integrarse con el mismo flujo de pago que reemplace el de `/reservar` (ver sección de integración futura), probablemente combinando ambos carritos (estadía + servicios) en un solo cobro.

## Nota sobre lint: `react-hooks/set-state-in-effect`

El ESLint de este proyecto (via `eslint-config-next`) incluye una regla estricta que marca como error llamar a `setState` dentro de un `useEffect` cuando el valor viene de una lectura/computación (como `JSON.parse` de `localStorage`). La hidratación de la sesión en `AuthProvider` es un caso legítimo de sincronización con un sistema externo al montar (no un efecto derivado en cadena), así que ahí se usa un `eslint-disable-next-line` puntual con comentario explicando el motivo. No copiar ese patrón de deshabilitar la regla para otros casos sin justificarlo de la misma forma — antes de hacerlo, intentar resolver el llamado de estado fuera del efecto (ej. `useState` con inicializador perezoso) cuando el componente no requiera compatibilidad con SSR.

## Infraestructura de Supabase (Auth ya conectada; resto del esquema listo, sin uso todavía en la UI)

El CLI de Supabase ya está inicializado para desarrollo local (carpeta `supabase/`, generada con `supabase init`), el esquema relacional inicial ya existe como migración SQL, y los clientes tipados de TypeScript ([lib/supabase/](lib/supabase)) ya están en uso real para autenticación (ver "Autenticación real con Supabase Auth + middleware" arriba). El resto de la UI (fotos, amenidades, servicios, tablas del panel admin) sigue leyendo de `lib/mock-data.ts`.

- **Levantar el entorno local**: `npx supabase start` (requiere Docker corriendo) levanta Postgres, Auth, Storage, Studio, etc. en contenedores locales; `npx supabase stop` los apaga. La primera vez descarga las imágenes de Docker, lo cual puede tardar varios minutos. Los contenedores no persisten entre reinicios de Docker/la máquina — si `docker ps` no muestra los contenedores de Supabase, hay que volver a correr `supabase start` antes de levantar `npm run dev` (el login real no funciona sin la base de datos local corriendo).
- **Variables de entorno**: `.env.local` (no versionado, ya está en `.gitignore` vía el patrón `.env*`) contiene `NEXT_PUBLIC_SUPABASE_URL` y `NEXT_PUBLIC_SUPABASE_ANON_KEY`, tomadas de la salida de `supabase start`. Si se reinicia el entorno local y las claves cambian, hay que actualizar este archivo a mano.
- **Clientes tipados** ([lib/supabase/](lib/supabase)): ya no es un único `lib/supabase.ts` — ver el detalle completo (client/server/middleware/env, y por qué llevan `"public"` explícito como segundo genérico) en la sección de autenticación arriba.
- **Tipos generados** ([lib/database.types.ts](lib/database.types.ts)): generados automáticamente con `npx supabase gen types typescript --local > lib/database.types.ts`. Es un archivo derivado — **no editar a mano**; regenerarlo cada vez que cambie el esquema (nueva migración, nueva tabla/columna/enum). El comando de `gen types` a veces mezcla una línea `Connecting to db 5432` de stderr al inicio del archivo si stdout/stderr no se separan explícitamente al redirigir — revisar la primera línea del archivo generado y borrarla si aparece, o redirigir stderr aparte (`2>/dev/null`).
- No conectar `CartContext`, `mock-data.ts` (fotos/amenidades/servicios/precios), ni `ReservationsTable` a Supabase hasta que se pida explícitamente. Hoy ya están conectados: Auth y el CRUD de usuarios de `UsersTable` (ver sección "CRUD de usuarios").

### Modelo relacional (migraciones `supabase/migrations/20260901072551_init_schema.sql` y `20260902053910_add_payment_status_and_finalizada_rename.sql`)

La primera migración crea las tablas, ENUMs y llaves foráneas descritas abajo, todas en el schema `public`. La segunda (ver "CRUD de reservaciones" más arriba) agrega el ENUM `payment_status_type` y la columna `reservations.payment_status`, y renombra el valor `pasada` del ENUM `reservation_status` a `finalizada`. `supabase/seed.sql` siembra datos de desarrollo que replican `lib/mock-data.ts` (usuarios, tarifas, menús de comida, vinos, masajistas) y se aplica junto con ambas migraciones al correr `npx supabase db reset`.

- **ENUMs**: `role_type` (`admin` | `holder` | `guest`), `profile_status` (`activo` | `invitado`), `reservation_status` (`pendiente` | `confirmada` | `cancelada` | `finalizada`), `meal_type` (`Desayuno` | `Almuerzo` | `Cena`), `payment_status_type` (`pendiente` | `parcial` | `completado` | `reembolsado`).
- **`profiles`**: `id` es PK y a la vez FK a `auth.users(id)` (`on delete cascade`) — un perfil no puede existir sin su usuario de Supabase Auth. Por eso `seed.sql` inserta primero en `auth.users` (con contraseña de desarrollo `changeme123`, usando `extensions.crypt`/`extensions.gen_salt` de `pgcrypto`) antes de insertar en `profiles` con el mismo `id`. Campos de nombre separados en `first_name` / `apellido_paterno` / `apellido_materno` (a diferencia del campo `nombre` único que tenía el antiguo `MockUser`, ya eliminado de `mock-data.ts` — ver "CRUD de usuarios").
- **`property_settings`** y **`fare_types`**: reemplazan `PRICING_CONFIG` y `FARE_OPTIONS` de `mock-data.ts` respectivamente.
- **`reservations`**: FK a `profiles` (`guest_id`) y `fare_types` (`fare_type_id`). Tiene dos estados independientes — `status` (`reservation_status`, ciclo de vida operativo) y `payment_status` (`payment_status_type`, agregado en la segunda migración, ciclo de vida del cobro) — ver "CRUD de reservaciones" más arriba para el detalle de por qué están separados. Usa **soft delete** vía la columna `deleted_at` (nullable, sin trigger todavía) — una reservación "eliminada" se marca con `deleted_at` en vez de borrarse con `DELETE`; cualquier query futura que liste reservaciones debe filtrar `deleted_at is null` explícitamente, ya que no hay una vista ni política que lo haga automáticamente. `status` es independiente del soft delete: una reservación puede estar `cancelada` (sigue existiendo, solo cambió de estado) sin tener `deleted_at`.
- **Servicios** (SPA, Comida, Vinos): cada uno sigue el patrón catálogo + booking — `spa_masseuses`/`spa_bookings`, `food_menus`/`food_bookings`, `wines`+`wine_packages`/`wine_orders`+`wine_order_items`. `spa_bookings`, `food_bookings`, `wine_orders` tienen FK a `reservations` (`on delete cascade`: si se borra la reservación físicamente, sus bookings de servicios se van con ella). `wine_order_items` permite líneas de botella individual o de paquete en el mismo pedido (`wine_id` y `wine_package_id` son mutuamente excluyentes vía `check` constraint), reflejando la unión `WineOrderBottle`/`packageQuantity` de `WineOrder` en `mock-data.ts`.
- **`seed.sql`** deliberadamente **no** siembra `reservations` ni las tablas de bookings: `mockReservations` en `mock-data.ts` referencia huéspedes (`"Laura Fernández"`, `"Jorge Salas"`) que no existen como perfiles reales (no están en el seed de `profiles` de arriba), así que no hay un mapeo limpio a `profiles` reales. Esas tablas quedan vacías pero con el esquema listo.
- **RLS deshabilitado a propósito**: ninguna tabla tiene Row Level Security activo todavía — todas son alcanzables por las claves `anon`/`authenticated` sin restricción. La migración termina con un comentario `-- TODO: Implement RLS policies for sensitive data (profiles, reservations) in a future migration before production.` — **no se debe conectar ningún componente real a `reservations`/las tablas de bookings sin antes crear esa migración de políticas RLS**, ya que hoy cualquier usuario con la `anon key` podría leer o modificar cualquier fila. `profiles` es la única excepción hecha hasta ahora (login/middleware, y desde esta fase también el CRUD de `app/admin/actions.ts` — ver sección "CRUD de usuarios"), y solo está protegida a nivel de aplicación (cada Server Action verifica `role === "admin"` antes de tocar la tabla), **no** a nivel de base de datos — la migración de RLS sigue pendiente y sigue siendo necesaria antes de producción.
- Cualquier cambio de esquema futuro debe ser una **migración nueva** (`npx supabase migration new <nombre>`), nunca editar `20260901072551_init_schema.sql` una vez aplicada en algún entorno compartido.

Antes de exponer estas tablas fuera del paraguas de las Server Actions actuales, hace falta la migración de políticas RLS pendiente (ver TODO en la migración inicial) — hoy cualquier usuario con la `anon key` puede leer/escribir cualquier fila de esas tablas directamente. `profiles` y `reservations` tienen el mismo problema de fondo (RLS deshabilitado a nivel de base de datos) aunque ya estén en uso real — ver la advertencia en "CRUD de usuarios" y "CRUD de reservaciones".
- **Registro real**: [app/register/page.tsx](app/register/page.tsx) sigue siendo un formulario 100% mock (`setSuccess(true)` sin llamar a Supabase) — no se tocó en la migración de Auth porque no se pidió explícitamente. Cuando se conecte, debe usar `supabase.auth.signUp()` y crear la fila correspondiente en `profiles`.
- **Stripe**: procesamiento real de pagos en el flujo de reservación (`app/reservar/page.tsx`), reemplazando la redirección directa a `/pago-exitoso` por un Stripe Checkout o Payment Intent, con confirmación por webhook antes de mostrar la página de éxito.
- **`sonner`**: notificaciones tipo toast globales (ej. confirmar "agregado al carrito", errores de guardado en el modal de `UsersTable.tsx`, feedback de acciones) — todavía no está instalada ni implementada; cuando se agregue, montar su `<Toaster />` en [app/layout.tsx](app/layout.tsx) junto a `AuthProvider`/`CartProvider`.
- Al conectar backend real, mantener `lib/mock-data.ts` como referencia de la forma (shape) de los datos, pero las fuentes de verdad pasarán a ser consultas a Supabase.

## Qué NO hacer

- La autenticación (Supabase Auth + middleware), el CRUD de usuarios y el CRUD de reservaciones del panel admin ya son reales — no volver a introducir un atajo mockeado (`localStorage`, estado local espejando props, verificación de email hardcodeado, etc.) para "simplificar" un flujo nuevo. Sí seguir sin conectar a base de datos real las partes explícitamente marcadas como pendientes arriba (`CartContext`, `/reservar`, `/register`) hasta que se pida.
- No introducir librerías de UI pesadas (component libraries completas, con estilos monolíticos propios) para este prototipo salvo que se solicite; preferir Tailwind puro y componentes propios. **Sí están permitidas** las siguientes herramientas por ser *headless* (sin estilos propios, se skinean 100% con Tailwind), de código abierto y costo $0: **`shadcn/ui`** (basada en Radix UI — componentes accesibles sin estilo propio), **`react-day-picker`** (calendarios, ver `components/Calendar.tsx`), **`sonner`** (notificaciones tipo toast — aún no instalada, ver "Integración futura planeada") y **`lucide-react`** (íconos del sistema, ver regla de íconos arriba). No agregar ninguna otra librería de UI (headless o no) sin que se pida explícitamente — esta lista es exhaustiva, no un precedente abierto.
- No romper la estructura de `lib/mock-data.ts` sin actualizar también `DOCUMENTATION.md`.
